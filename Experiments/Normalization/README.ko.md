# 정규화 언어 시험

[English](README.md) · **한국어**

결정: 제품의 Swift·C# 구현을 유지합니다. Rust는 실제 Swift C import와 C# P/Invoke 호출에서 Windows의 보정된 0 증가분 근거를 포함해 양쪽 정규화 계약과 일치했습니다. 단독 계산은 빨랐지만 합성 파싱 경로 측정만으로 제품 빌드 체계 하나와 연결 계층 두 개를 추가할 근거는 부족합니다. 앱 빌드 대상은 이 시험에 의존하지 않습니다.

## 재현

Swift·Rust·.NET 10이 설치된 macOS에서 저장소 루트 기준으로 실행합니다.

```sh
python3 Experiments/Normalization/run.py
```

실행기는 `.build/normalization-trial`에 빌드하고 Rust 단위 검사와 공통 13개 시나리오·31개 상태 전이를 실제 바인딩으로 실행한 뒤 벤치마크 체크섬을 확인합니다. C 메모리 배치는 Rust·Swift·C#에서 확인합니다. Cargo·NuGet 의존성을 추가하지 않았습니다. Swift 실행기는 앱·DB·제공업체 프레임워크와 독립적으로 제품 값 타입·파서·정규화 코드를 컴파일합니다. C# 프로젝트도 해당 제품 소스 파일을 직접 연결합니다.

각 프로세스는 네 번 실행하고 첫 시간 표본을 제외합니다. 매회 정규화는 1,000,000번, JSON 파싱과 정규화는 20,000번입니다. 실행 중 JIT 최적화 단계가 바뀌어 파싱 경로 속도가 달라 보이지 않도록 해당 .NET 프로세스의 계층별 컴파일을 끕니다. 합성·단일 스레드·메모리 입력이며 파일·SQLite·화면·네트워크·실제 Windows 실행은 포함하지 않습니다.

## 기록한 결과

[기준 결과](baseline-macos-arm64.json)는 기존 C# 참조 레코드 상태·결과를, [최종 결과](results-macos-arm64.json)는 읽기 전용 값 레코드를 사용합니다. 보고서에는 도구 버전·입력 해시·모든 시간 표본·프로세스 최대 메모리가 있습니다. 기준 상태를 재현하려면 두 값 레코드 선언을 `sealed record`로 바꾸고, 상태 인자의 `in`을 제거하고, null 검사를 복원한 뒤 시험을 실행합니다. 이후 제품 소스를 원복합니다.

| 최종 교차 실행 | 기존 언어 정규화 | 바인딩을 통한 Rust | 기존 언어 파싱 경로 | Rust 파싱 경로 |
| --- | --- | --- | --- | --- |
| Swift | 26.94 ns/호출 | 6.87 ns/호출 | 5,710 ns/행 | 5,786 ns/행 |
| C# | 39.57 ns/호출 | 8.82 ns/호출 | 2,479 ns/행 | 2,365 ns/행 |

이번 실행의 파싱 경로에서 Rust는 Swift보다 약 1.3% 느렸고 C#보다 약 4.6% 빨랐습니다. 통계적 신뢰 구간이나 앱 전체 속도에 대한 주장은 아닙니다. 개별 기존 언어·Rust 프로세스의 최대 메모리는 Swift 약 62.5 MB, C# 약 63.3 MB로 Rust의 의미 있는 메모리 이점은 확인되지 않았습니다. 최대 RSS에는 런타임·fixture·파서·사전 검사가 포함되며 계산 함수의 힙 사용량을 뜻하지 않습니다.

C# 값 레코드 변경은 상태·결과 객체의 힙 할당을 제거합니다. 정규화 100만 회 기준 기존 관리 힙 할당은 180,903,272바이트, 최종 실행은 벤치마크 타이머에 해당하는 40바이트였습니다. 별도 회귀 테스트는 준비된 정규화 반복문 내부의 할당이 0인지 확인합니다. 할당 개선이며 정규화 속도가 빨라진다는 약속은 아닙니다. 기록된 단독 계산에서는 기존 참조 레코드가 더 빨랐습니다.

## 유지보수 결정

의존성 없는 Rust 시험은 재현 근거로 보존하고 제품 패키징에서는 제외합니다. 동작 fixture를 공유하고 플랫폼 작업은 기존 경계에 유지합니다. 향후 Rust 제안에는 실제 전체 경로의 병목 또는 ABI 소유권·릴리스 패키징·실제 x64/ARM64 검증 비용을 정당화하는 중복 유지보수 감소가 필요합니다. 이번 시험은 그 이점을 입증하지 않습니다.
